# Native transport boundary

The BCAP encoder interoperates with the C++ core. The experimental CEP UTF-16 string carrier is implemented as a bounded encoding helper; this module does not itself mutate the running effect. Parameter edit and migration functions create plans; they do not mutate Premiere.

Current primary documentation inspected on 2026-10-18:

- [Adobe UXP Component](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/component): `getMatchName`, `getParamCount`, and zero-based `getParam` support a read-only inventory of an existing component. Index order is component-defined, and must not be confused with PF disk IDs.
- [Adobe UXP ComponentParam](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/componentparam): `createKeyframe` accepts number, string, boolean, PointF or Color **depending on the parameter type**; incompatible types throw. `createSetValueAction` concerns non-time-varying values. This is insufficient evidence that a string can set a PF arbitrary-data parameter.
- [Adobe UXP Keyframe](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/keyframe): documents its value and temporal interpolation access. It does not establish arbitrary binary transport.
- Adobe After Effects SDK 26.5 `Examples/Headers/AE_Effect.h` defines `PF_Arbitrary_PRINT_SIZE_FUNC`, `PF_Arbitrary_PRINT_FUNC`, and `PF_Arbitrary_SCAN_FUNC`. PRINT returns a text description; SCAN reconstructs an arbitrary handle from text. Their existence does not prove Premiere calls SCAN for CEP `setValue(string)` or UXP `createKeyframe(string)`.

`probeNativeComponent` uses only the documented read APIs against a caller-resolved native component, returns bounded observations, and intentionally reports write/arbitrary transport support as unverified. It does not add effects or change any parameter. Tests use structural mocks; no live host proof is implied.

A host experiment observed an exact ASCII string getter after CEP `setValue(string)`, but this did not establish the native callback route or renderer input. A later fresh-effect read returned raw BCAP interpreted as UTF-16 (`䍂偁\u0001`) despite a UTF-16 in-memory default. The current evidence is consistent with CEP exposing FLATTEN output to getters and passing setter data through UNFLATTEN; this remains a callback-routing inference until instrumented host verification. The adapter is being changed to provide a readable UTF-16 BCDOC1 carrier through FLATTEN too. No SCAN bypass or direct raw-handle setter is established. Full native rendering and save/reopen proof remain separate host checks. A failed or uncertain mutation must not be retried automatically. If the host does not expose this bridge, investigate a documented native custom UI/import mechanism and make the limitation explicit; never quietly substitute a sidecar movie.

Any resulting adapter must preserve effect instance and clip identity, exact ticks, all unrelated keys/interpolation, original native Motion, source transcript, manual splits and legacy containers. A per-time reset must use the native parameter default and retain other keys. These are requirements, not verified host behavior.

## Compiled adapter parameter identities

The current `native/adobe/BetterCaptionsEffect.cpp` defines stable disk IDs: **1 Position (point), 2 Width, 3 Height, 4 Characters per caption, 5 Global font size (64 = 1x), 6 Global text tint, 7 Caption document (experimental, arbitrary)**. Disk IDs describe native serialization identities. They are **not** documented UXP component indexes; the host inventory must determine the actual exposed ordering.

Global font size multiplies every document state’s font size by the native value divided by 64; default 64 is neutral. Global text tint multiplies state RGB by the native tint; white is neutral and state alpha/opacity are retained. These controls do not replace the independent document styles.

Panel logical `positionX` and `positionY` both refer to coordinates of the **same Position point parameter**, representing the text-area center in the compiled renderer. An adapter must read the existing point at the requested ticks, update one coordinate, and preserve the other coordinate and native keyframe interpolation. It must verify Premiere’s coordinate units before exposing pixel labels; the compiled renderer interprets the supplied PF point values as pixels before render-resolution scaling. Width/Height each permit 1–8192 in the native parameter definition. Their independent values control reflow, without a scale/aspect-ratio operation.

`NATIVE_PARAMETER_DISK_MAPPING` records these native source identities without assuming host parameter indexes or claiming a completed writable bridge.

## Host discovery and Position conversion

The host investigation observed CEP's exact component match name as `AE.com.swen.bettercaptions.native.experimental`. `normalizeNativeMatchName` accepts that single known prefix and the canonical match name only. It does not strip arbitrary prefixes, change case, or trim input.

The [CEP ComponentParam documentation](https://ppro-scripting.docsforadobe.dev/sequence/componentparam/) specifies appropriate parameter types for `setValue` and generic values for `setValueAtKey`, but does not define a universal point representation or coordinate units. Adobe's [UXP PointF](https://developer.adobe.com/premiere-pro/uxp/ppro-reference/classes/pointf/) has numeric X/Y coordinates, and ComponentParam accepts PointF for compatible parameters; neither documents that an effect's point coordinates universally use sequence pixels or normalized coordinates.

`planNativePointCoordinate` therefore requires rendering-verified coordinate calibration for the exact target/revision. It can convert a pixel coordinate to a normalized sequence coordinate using sequence width/height, or preserve pixel units when the host has proved them. It retains the untouched coordinate from the same host point and emits no host mutation. Numeric getter equality alone is insufficient calibration: the investigation reported that some point writes read back but did not produce expected visible placement. No current calibration is bundled or assumed.

## BCDOC1 UTF-16 carrier

The isolated host experiment observed exact ASCII readback after CEP `setValue('BCDOC1:' + hex(BCAP), 1)`. `encodeNativeTransportText` implements this carrier encoding without invoking the host. The native adapter must recognize UTF-16 carrier input in UNFLATTEN and provide readable carrier output in FLATTEN before the panel can rely on the getter for revision/readback. An observed setter input omitted the UTF-16 terminator; the native parser must accept that representation as well as its own terminated allocations. The JSON panel protocol remains version 1; the binary BCAP codec is version 2 with a persistent time origin. The native core also reads legacy BCAP version 1 with an origin of zero. Binary `getValue` is unsuitable as a roundtrip mechanism because the host exposed a truncated UTF-16 string at the first null.

The panel conservatively budgets the native allocation for a terminating UTF-16 null even when CEP omits it from the setter payload. For N BCAP bytes the native carrier consumes `2 * (7 + 2*N + 1)` bytes; the helper caps BCAP at **4,194,300 bytes** before constructing hex or returning a sendable string. The binary core's separate 16 MiB cap remains unchanged. Tests cover exact Unicode source byte recovery, ASCII-only output, terminator accounting, and rejection of a valid binary document that exceeds the text-carrier budget. Exact string readback alone is not evidence of native rendering or persistence.

## Guarded existing-container CEP operations

`cep-operations.ts` generates real ExtendScript source for the caller's explicitly selected CEP bridge. Script generation is pure: nothing executes automatically. `buildCepNativeReadScript(locator)` reads one exact project path, active sequence ID, clip node ID, track/clip/component/parameter indexes, native match name, and document parameter label. It rejects a time-varying document, binary/truncated getter, malformed carrier, or oversized data.

The returned opaque revision includes project/sequence/clip identity, clip start/end/in/out ticks, the complete component match-name ordering, the document parameter index, and exact existing carrier. `buildCepNativeDocumentApplyScript(snapshot, document, true, mode)` requires explicit consent and matching document sequence. The generated host script reads current state again and compares the exact revision **before** invoking one `setValue(carrier, 1)` call. It immediately reads back the exact carrier. A setter acknowledgement alone is not accepted as readback or rendering proof. Exceptions after attempting the setter and unequal readbacks are marked uncertain, with no automatic retry. The source snapshot contains the original carrier for explicit restoration.

These helpers update an already selected native adjustment-layer container only. They do not create effects, import footage, migrate legacy captions, alter tracks, change clip timing, write scalar controls/keyframes, or replace Motion. Caller-owned migration must remain explicit and reversible. The revision covers the document and clip/component identity; unrelated scalar/keyframe edits are preserved by not writing them. CEP provides no persistent component instance ID here, so indistinguishable duplicate native effect instances cannot be distinguished beyond index, ordering, and document content. The helper rejects multiple native effect instances on the selected clip as ambiguous.

Generated scripts are exercised with mocked Premiere objects, including stale project/sequence/clip/effect/timing failures, exact readback, no automatic retries after an uncertain setter, and fail-closed binary getters. These tests do not claim installed-host execution of the new helper. The existing root-owned scratch host experiment establishes exact ASCII getter readback for one setter experiment, but not the native callback path; the helper remains fail-closed for raw binary getters until the revised FLATTEN/UNFLATTEN path is host-tested; rendering, save/reopen, and migration remain independent acceptance checks.

## Adjustment layers only

Native Better Captions must be applied to adjustment layers, never footage clips. The [documented CEP TrackItem.isAdjustmentLayer()](https://ppro-scripting.docsforadobe.dev/item/trackitem/#trackitemisadjustmentlayer) returns a Boolean. Both generated read and apply operations require that exact method to exist and return **true** on the selected timeline item. Missing methods, false, numeric 1, string "true", and thrown errors fail closed before any setter. Names such as "Adjustment Layer" or project-item file metadata are not used as substitutes. The returned revision includes the confirmed adjustment-layer role.

Pure migration plans likewise require `snapshot.adjustmentLayer === true` and report `targetKind: 'adjustment-layer'`; execution still needs the live host check. The guard does not create a layer, choose a track, or move anything. A caller implementing creation must choose/create a clear track above footage and preserve existing clip identities, timing, effects and native Motion. The root-owned host probe confirmed that Premiere exposes this method as a function and that the inspected footage clip returns false. Positive detection and guarded apply on an actual adjustment layer remain separate acceptance checks.

## Persistent adjustment-layer time origin

JSON native documents remain protocol version 1. An optional `timeOriginSeconds` is normalized to zero when absent and must be finite within ±864000 seconds. BCAP binary codec version 2 appends this value as a little-endian f64 after the former v1 final Title Case flag. The native decoder accepts v1 and upgrades its absent origin to zero; new encoders emit v2. Binary codec and JSON protocol version numbers are deliberately separate.

For an explicit guarded **initial attachment**, the panel helper derives the origin from the captured adjustment-layer snapshot as `(inPointTicks - startTicks) / 254016000000`. It validates both signed decimal tick strings with BigInt arithmetic and bounds before conversion, and overrides any caller-supplied origin. Source transcript word times remain unchanged and sequence-relative. The same exact revision is checked again immediately before the host setter, so moving, trimming or splitting the layer after capture fails closed. Persisting the origin is intended to retain the original time mapping across later native Razor splits and layer moves, instead of deriving a fresh origin every rendered frame. This intent is not yet accepted behavior: the current host test reported a blank right-hand clip immediately after a split at four seconds when viewed at five seconds, while moving that clip to start at ten produced a visible caption at eleven. Split, move and save/reopen behavior remain open acceptance items.

The apply helper requires an explicit fourth mode argument. `initial-attachment` captures the snapshot-derived origin for first attachment or a deliberate new anchor. `edit-existing` instead parses the origin from the **currently read host carrier in the snapshot**, ignoring caller-supplied origin and the layer’s current start/in point. Its bounded reader walks the complete BCAP layout, validates supported versions, strings, counts, styles, timing and exact payload ending, then accepts the origin. Legacy v1 carries an origin of zero. Missing/unknown mode is rejected. Both modes retain the exact revision guard, so an intervening move or split prevents a write until a fresh read.

This resolves the panel-side risk of silently re-anchoring a content edit after a layer move or split; it does not resolve the current native host split-render issue. A mock regression starts with origin3600/right-half start4/in3604, moves the half to start10, rejects the stale revision, then edits with a fresh revision while preserving origin3600 despite a conflicting caller origin. No installed-host timing acceptance is implied.

Tests cover nonzero v2 TS/C++ byte equality, legacy v1 decode and canonical v2 upgrade, invalid/nonfinite/out-of-range origins, malformed/oversized tick strings, caller-origin override, and unchanged source word timing.

## Timeline cadence and remaining enforcement boundaries

Native BCAP documents store time in seconds and do not specify output FPS. Premiere supplies the native effect render cadence; changing source-file FPS must not select caption cadence. The ordinary source-time helper uses the host rate to convert clip-start frames to seconds, which is a time-coordinate conversion rather than an output-frame-rate override. A source-24/sequence-30 regression covers that distinction. The separate panel/movie exporter passes active sequence FPS through rendering, FFmpeg and FFprobe; no equivalent FPS field should silently take authority in the native document. Fractional rates and live sequence-rate changes still need their own host acceptance coverage.

Only the generated existing-container CEP read/apply operations enforce adjustment-layer eligibility at runtime. Pure parameter plans, the UXP component-only read probe, and codec validation do not have a TrackItem and cannot establish its role. They must not be treated as authorization to write arbitrary footage effects. Migration plans require a positive supplied layer-role snapshot but still need the live guard when executed. No track-creation/placement binding exists here, so the requirement to choose a clear track above footage remains unenforced by these helpers. The existing helper also does not inspect track locks; a future mutation binding must respect current track eligibility rather than assuming that a valid index makes a track writable.


BCAP binary v5 adds `bubbleFillSpaces` for upcoming/current/spoken appearances as three bounded uint32 booleans after the v4 case footer. The JSON protocol version stays 1. Absent/false values leave v1–4 carriers byte-identical; a true value requires the matching v5 native renderer. Both the full panel reader and the origin-only structural reader validate the complete footer and reject malformed flags or trailing bytes. Turning the option off preserves an already-v5 carrier rather than downgrading its format. This is document styling, not an additional Effect Controls parameter or animation authority.


BCAP v6 keeps all prior bytes and appends 48 bytes of axis padding (upcoming inline/block, current inline/block, spoken inline/block; binary64, -1 unset or finite 0–4096), then three uint32 underline modes (upcoming/current/spoken: 0 unset, 1 off, 2 on). Optional JSON properties are `bubblePaddingInline`, `bubblePaddingBlock`, and `underline`. Each padding axis falls back independently to the state's existing `padding`. Absent overrides leave v1–5 carriers byte-identical. Explicit false underline also requires v6, preserving its difference from unset. Both bounded TypeScript readers and the native decoder validate the entire footer; CEP append-only extension validates it before duration mutation and preserves its raw bytes.
